# 审批与附件

## 审批

使用预置 View 和实时动作完成审批：

1. 用 `find view pending-approvals` 取得当前用户可处理的待办候选，并处理完整分页。
2. 按业务对象、编码、提交人和到达时间展示必要摘要；列表顺序不是用户选择。
3. 用待办返回的业务 `RecordRef` 读取必要详情。
4. 用 `describe actions <RecordRef>` 重新确认此刻允许的动作；View 中的 actions 只用于导航。
5. 向用户展示具体单据、决定和意见，然后用 `do-action` 执行一次。
6. 根据返回记录、待办变化和必要的最小读取确认结果。

## 单据审批动作清单

预置的单据审批动作只有以下这些，表中第一列就是 `do-action` 要传的 `actionId`。不存在 `approve` 与 `reject` 这两个动作，也不要把平台功能权限里的动作位当成 `actionId`：

| actionId | 含义 | 可用前提 |
| --- | --- | --- |
| `submit` | 提交 | 草稿、已撤回或重新开始，且当前用户是创建人，且非模板单 |
| `recall` | 撤回 | 已提交或审批中，且当前用户可终止该流程 |
| `recall-approved` | 撤回已审 | 审批中且非变更单，当前用户可撤销本人已审节点 |
| `agree` | 同意 | 当前用户有该单据的待审批任务 |
| `deny` | 驳回到提交人 | 同上 |
| `back` | 驳回到上一级 | 同上 |
| `retry` | 重试 | 当前用户有该单据的异常审批待办 |
| `unapprove` | 弃审 | 已生效，且未处于变更、异常或挂起状态 |

驳回必须先与用户确认退回到哪一级：`deny` 退回提交人并终止当前审批路径，`back` 只退回上一级节点。两者不能互换，也不能用其中一个代替用户表达的另一种意图。

这些动作对全部单据类对象通用，档案类对象没有它们。可用前提由服务端按当前记录和当前用户实时判定，因此同一状态的单据对不同用户可用动作不同，每次都以 `describe actions` 的返回为准。全部动作都只接受一个可选的 `reason` 意见参数。

每次处理明确的待办目标。用户要求批量处理时仍逐条核对目标和实时动作，不能因为首条成功就假设后续记录状态相同。结果不明确时按写入恢复规则处理，不自动重复审批。

## 列出附件

使用 `records attachments list <RecordRef> [--scope self|all] [--offset <n>] [--limit <n>]` 查看附件元信息，该命令不返回任何访问地址：

- 默认 `--scope self`，只列 `ownerRef` 指向该记录自身的附件。
- `--scope all` 只在此之上追加两类：主记录上直接外键指向附件的单槽位，以及该记录直接明细子表行上的附件。它不沿外键展开到其它业务对象，不存在跨对象的附件图谱。
- 结果分页，缺省 `--limit 20`，取值 1 到 100。需要全集时按 `hasMore` 继续翻页，不能用首页代替全集。
- `ownerRef` 表示附件真实归属记录，可作为 `url` 与 `upload` 的目标 ref 使用；`slot` 表示所在槽位，`slotKind` 取 `list`（多态附件集合）或 `single`（单外键槽位），这两者只解释业务位置，不作为输入参数。
- 多个附件按名称、大小、上传人、上传时间和 `ownerRef` 消歧。

主记录不存在或当前身份不可见时命令整体失败，不会退化为成功的空列表。因此成功且 `total: 0` 就表示该作用域内确实没有附件，不需要再怀疑权限。`list` 与 `url` 共用同一个附件查看权限门槛，不存在能列举却不能签出地址的中间状态。

## 签出访问地址

使用 `records attachments url <RecordRef> [--attachment-id <id1,id2>] [--expires <seconds>]` 为附件签发有时效的访问地址：

- 附件 ID 只接受逗号分隔数组，单次最多 50 个。不要用空格分隔的多个位置参数，CLI 不接受该形态。
- 省略 `--attachment-id` 时返回的集合与同一记录 `--scope self` 的列举结果逐条相等，既不含明细行附件也不含单外键槽位附件。要取这两类附件的地址，先用 `--scope all` 读到它们的 `ownerRef`，再对该 `ownerRef` 执行 `url`。
- 附件 ID 只能在其真实归属记录的作用域内使用。传入不属于该记录或不存在的 ID 时整个请求失败、不返回任何地址，不会只跳过该条。
- 单条附件可能只带 `unavailableReason` 而没有地址，例如存放在第三方存储，此时整批请求仍然成功。逐条确认是否拿到地址，不能因为命令成功就假设每个 ID 都已签出。
- `--expires` 只是期望秒数，实际到期时间以返回的 `expiresAt` 为准；省略时沿用平台默认有效期。

拿到地址不等于文件已经下载、读取或解析。只有任务需要且 Agent 具备文件访问能力时才继续处理；地址过期后重新签发仍受当前身份和业务记录权限约束。

## 上传附件

使用 `records attachments upload <RecordRef> --file <path> [--name <name>]` 追加单个附件：

1. 确认目标记录、用户上传意图和本地文件路径。
2. 确认文件存在且可读。不要用本地常量判断大小是否允许：唯一的大小裁决在服务端，超过当前环境分片阈值时返回 `ATTACHMENT_UPLOAD_MULTIPART_UNSUPPORTED` 并回传实际阈值，此时改用 Web 端上传。
3. 不传 `--slot`、`--field` 或替换模式。附件固定追加到记录的多态附件集合，单外键槽位本版本只读；记录不具备多态集合时返回 `ATTACHMENT_UPLOAD_UNSUPPORTED`。
4. `--name` 只改附件展示名，不影响存储路径；省略时使用本地文件名。
5. `<RecordRef>` 同时接受主记录 ref 与明细子表行 ref，可以直接使用 `--scope all` 返回的 `ownerRef`。
6. 只有最终返回新增附件记录才报告上传成功。命令内部先申请上传授权、再直传文件、最后挂接附件，前两步完成都只是中间状态；过程提示走 stderr，业务结果在 stdout。一次 upload 消耗两个 operation 的调用预算。

上传是写入纪律中少数可以直接重跑的操作：幂等键由目标记录与文件内容确定性派生，同一记录、同一份未修改的文件重跑，在幂等窗口内不会产生重复附件。据此区分三种失败：

- 申请授权或直传阶段失败：重新执行同一条命令。
- 挂接阶段失败：文件可能已上传但未挂接到记录，重跑同一命令；仍失败则联系管理员清理未挂接文件。
- 返回 `ATTACHMENT_STORAGE_QUOTA_EXCEEDED`：附件已经保存，只是租户存储空间超限。不要重试，重试只会再写入一条。

幂等窗口之外重复上传同名同内容文件会得到两条附件记录，服务端不做去重。首版本不提供下载、替换、删除、重命名、排序与分片续传命令，取文件一律经由 `url` 签出的地址。受限环境无法读取本地文件时应本地失败，不发起后续业务提交。
