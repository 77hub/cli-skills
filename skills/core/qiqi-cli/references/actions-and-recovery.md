# 记录动作、删除与结果恢复

## 发现并执行记录动作

对单据提交、撤回以及其它通用单记录动作：

1. 用稳定 `RecordRef` 确认目标记录和当前状态。
2. 用 `describe actions <RecordRef>` 读取此刻允许的动作及其 `inputSchema`。`do-action` 没有针对单个动作的帮助，`--help` 只能用于 `do-action` 自身，动作的参数定义只能从这一步得到。
3. 核对用户意图、动作 ID 和必需参数。
4. 用 `do-action <RecordRef> <actionId>` 执行一次。
5. 依据返回记录或后续最小读取确认结果。

可用的单据动作及其可用前提见 [approvals-and-attachments.md](approvals-and-attachments.md) 的动作清单。不要直接改写状态字段，也不要仅凭其它记录曾经支持某动作就假设当前记录同样支持。qiqi 已提供专用业务命令的流程必须使用该专用命令，不用名称相近的 `do-action` 代替。

传参有三种互斥形态：逐字段选项、`--data <json>`、`--data-file <path>`。逐字段选项不能与后两者混用，`--data` 与 `--data-file` 也不能同时给；动作没有 `inputSchema` 时不接受任何业务参数。数组和嵌套对象优先使用 `--data-file`，避免内联 JSON 的转义问题。

动作 ID 传错时命令会失败并返回当前可用动作候选，可据此纠正，但不要用穷试代替第 2 步的确认。

`--yes` 只在服务端把动作标记为高风险时才必填，当前预置动作都没有声明高风险，通常不需要传。这不降低确认要求：执行前仍必须向用户明确单据、动作和影响。

## 两阶段删除

`records delete <RecordRef>` 使用两阶段协议：

1. 不加 `--yes` 执行预检查，核对目标摘要、可见性和确认提示；此时没有删除。
2. 用户已经明确要求删除且目标无歧义时，执行同一目标的 `records delete <RecordRef> --yes`。
3. 只有最终结果明确包含 `deleted: true` 才报告删除成功。

预检查成功、`confirmationRequired: true`、命令已发送或再次读取不到记录都不能单独替代 `deleted: true`。执行阶段仍由服务端重新校验权限和业务约束。

## 写入结果分类

| 结果 | 表达与后续动作 |
| --- | --- |
| 返回明确业务成功事实 | 报告已完成，并保留稳定引用和关键状态 |
| 返回明确业务失败 | 说明安全业务问题，不换参数绕过规则 |
| 定义过期 | 重新读取帮助或动作描述，重新评估后再决定是否执行 |
| 超时、连接中断或响应不完整 | 标记“状态未知”，先查询业务事实，不直接重试 |
| 只完成上传、预检查或其它中间步骤 | 报告中间状态，不表述为业务完成 |

`retryable: true` 不等于写操作可自动重放。一次新的 CLI 调用可能代表新的业务意图；没有确认前不要依赖新调用自动生成的幂等信息防重。

## 状态未知时的核查

优先选择最窄、最稳定的验证方式：

- 已知 `RecordRef`：用 `records get` 核对状态和关键字段。
- 已知唯一业务编码：用 `find list` 精确过滤并确认唯一记录。
- 工作列表变化：重新读取对应 View，但不把列表消失单独当作动作成功证明。
- 创建类命令：结合返回前已知项目、名称、负责人、日期和时间窗口查找候选，仍无法唯一确认时保持未知。

核查只能确认当前事实，不能补造原调用的成功响应。仍有歧义时把候选和未知状态交给用户决定。
